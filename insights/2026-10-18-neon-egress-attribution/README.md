# Neon 出站流量来源核查

核查日期：2026-10-18。范围：当前代码、正式域名部署、Neon 控制台与可访问的 Vercel 运行日志。仅做读取与分析，不修改业务代码、数据库、套餐或生产配置。

后续状态：下文保留优化前 `377fd83` 的核查结论。随后用户授权“优化”，本地已完成后台小字段轮询与按需详情，2026-10-19 进入 PR 交付；验证与范围见 [进展看板](../../docs/PROGRESS.md)。合并与部署需另行回读，不能据此认为线上已经减少流量或恢复配额。

## 结论

[事实] 控制台显示本账期网络传输累计 5.53 GB，项目为 Free，已因月网络传输额度耗尽暂停。这里是 Neon 向客户端返回的数据，不是数据库容量，也不是 OpenRouter 模型费用。

[推断] 应优先排查三个重复大对象读取路径：公开页面按请求取整个信号目录、生成进度轮询读取原文快照、自动化后台轮询读取最近 100 条任务的大字段。源码能证明这些读取发生，但不能证明它们分别占 5.53 GB 的多少，更不能据此排除运维和其他客户端。

[事实] 正式域名当前指向的 Production READY 部署提交为 `377fd83eeeac0d66ecdb39be9bad2d7bd3e46e4e`，包含 PR #222 的公开读取缩减。部署代码生效不表示数据库配额已恢复，也不表示已测得月度节省。

## 读取路径

| 路径                               | 代码可确认的行为                                                                                                         | 归因边界                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 首页雷达、信号列表、资源及综合搜索 | 统一模式下读取 `unified_public_signals.content` 的整批公开目录，然后在应用中聚合或筛选；React 缓存仅复用同次服务器渲染   | 访问/预取次数与响应字节未按月记录，不能确定占比                              |
| AI 生成任务进度                    | 活跃任务每 5 秒查询；数据库单任务读取包含 `snapshot`，创建时其中保存 `source`；浏览器 DTO 排除原文发生在数据库已返回之后 | 原文越大、运行越久、同时打开的轮询页面越多，潜在出站量越大；尚无实际字节计数 |
| 自动采集/专题任务后台              | 页面可见且有活跃任务等条件满足时，每 5 秒读取 dashboard；最近 100 条 run 包含 `snapshot,result,frozen_inputs`            | 读取的是历史任务大字段，不仅活跃任务状态；需实际行大小与页面使用时长才能量化 |
| 生成执行、审核/补证                | 生成前后从 `import_outputs.content` 读取解析正文用于原文与权限校验                                                       | 部分读取是完整性要求，不能为省流量直接移除校验                               |
| 健康检查和维护                     | 健康调度为每小时；统一模式只探测最多一条信号；人工维护部分步骤读取完整迁移源记录                                         | 不能把所有定时 CI 当成读生产库；维护也可能贡献历史流量                       |

## 已优化与未优化

[事实] PR #222 已将普通详情改为按 ID 读取，将统一模式健康探测缩为最多一条，把 pgvector manifest 比较放进 PostgreSQL 并返回布尔值，同时消除同次渲染的一部分重复读取。

[事实] 它没有实现公开目录跨请求缓存，也没有解决上述后台轮询携带全文。旧姓名匹配兼容路径仍可能让详情回退到全量目录。专题洞察开关开启时，部分公开页面还会读取全部已发布报告的完整 `result`，但本次未读取该生产开关，不能将其写成已发生的流量。

## 数据质量、局限与替代解释

- Neon 官方明确没有逐 SQL 或逐连接的网络传输分摊。免费计划的项目/分支累计值也不是逐日明细；付费 Consumption API 的时间序列仍需与操作记录关联。
- Neon 查询性能页在配额暂停状态下未取得可用查询统计；没有重启计算、重置统计或执行 SQL。
- Vercel 返回当前 Hobby 套餐不能访问本月完整运行日志（保留窗口为 1 小时）。最近 50 分钟取得的分组结果是日志条数，不是成功请求数，更不是 Neon 字节数，且处于数据库已暂停后的窗口，不能用来解释之前累计流量。
- 正式域名部署与源码一致，只验证代码版本，不验证各生产开关。代码路径描述明确注明模式条件。
- 机器人抓取、链接预取、人工验收、备份导出或其他连接都可能贡献流量。没有调用者及返回字节遥测，不应断言正常访客或 AI 是主要责任方。
- PR #222 历史单页缩减百分比属于估算，本次没有把这些数字作为实际账单证据。

## 建议顺序（核查时尚未实施）

1. 将轮询改用专用状态投影：SQL 层不读原文快照、完整结果与冻结输入；详情按需读取。保持 owner 过滤、状态与费用语义、取消/发布一致性。
2. 自动化 dashboard 只取列表摘要，并单独查询活跃任务状态；历史结果按需展开。
3. 公开页按用途读取摘要/聚合结果，搜索与资源过滤尽量下推到 SQL；若引入跨请求缓存，必须同时设计发布与撤回失效，不能直接长期缓存公开全集。
4. 在恢复可用后记录低敏感的查询用途、调用次数、行数和应用层结果大小，并对照 Neon 的周期总量。应用结果大小只是近似值，不等于完整 PostgreSQL wire/计费字节。
