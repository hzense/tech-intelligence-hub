# 统一 Signal 存储阶段 B：兼容迁移

本地实现 · 2026-10-05 · 未生产执行。目标是让原两张主表容纳 4.0，不在本批启用统一发布。

## 问题、目标与非目标

[事实] 0004 强制 `strength` 等列；0007 封存已提交版本；0012 对整行版本生成依赖封印。
因此不能直接删列、伪造评分，或仅新增列而忽略旧封印变化。目标是保留旧数据与可验证约束，提供可测试的 4.0 存储分支。
非目标：本批不回填、不授予新角色、不接通业务写入／公开视图、不执行生产维护。

## 方案比较

| 方案                 | 收益                           | 代价／失效风险                                    |
| -------------------- | ------------------------------ | ------------------------------------------------- |
| 新建独立 4.0 主表    | 旧表与约束完全不动             | 延续多套正式主存储，不符合本次目标                |
| 原表版本分支（采用） | ID／外键目标保留，统一版本正文 | nullable 必须配合严格分支约束，旧整行封印必须兼容 |
| 直接替换原列与旧约束 | 最终结构简单                   | 破坏封存与旧 writer，不能安全渐进交付             |

## 详细设计

[事实] 0029 的 3.0 分支保持旧字段非空，4.0 只在 `signal_versions.content` 存正文。
`signals.latest_version` 用延迟复合 FK 和提交时 max/count 检查保证完整连续历史。新增 guard 禁止 schema／origin 改写、跨主表版本串写、4.0 混入旧发表与关系链。
本批 4.0 仅表所有者可写，旧 ACL 不扩展；正式状态不等于公开许可。SQL 校验存储封装，完整内容政策仍在 JS 契约，后续 writer 必须双重验证。
旧 seal 函数从 snapshot JSON 排除新增六列，不更新既有 seal，保留原 UTC／权限属性。工作台沿原列级权限过滤 `title IS NOT NULL`。

## 迁移、验证与回退

只新增 0029，旧迁移与摘要不变；核验固定校验新列、检查、外键延迟、触发器及函数正文。
本地定向 PostgreSQL 采用显式 no-vector fixture；CI 必须执行原始全迁移与 pgvector，并升级真实已发布 3.0 链验证公开内容不变。
部署代码不能自动执行 SQL。生产前仍需新批准、备份、维护冻结、ACL 审查、独立核验。DDL 后应用可保留旧入口；不能盲目删新列回滚，尤其有 4.0 数据之后。

## 风险与反面观点

- 新增列导致旧 seal 失效：使用旧字段投影并对比完整 JSON；真实已发布链升级测试待完整环境运行。
- SQL 三值逻辑放行 NULL：分支最外层 `IS TRUE`；缺元数据、必填旧列、无 head 均负向测试。
- 旧 writer 被误授新列：owner-only guard 保底；未来专用 writer 改动需另行权限评审。
- [推断] 延迟 max/count 检查在十倍当前数据量仍可按主键 signal_id 聚合，但本批未做性能测量；长历史批量导入应测执行耗时与锁等待。
- 最强反对意见：过渡列使数据库复杂。回应：这是兼容阶段，不会永久维持两份正文；清理旧列必须等统一迁移和封存兼容完成，不能提前删。
