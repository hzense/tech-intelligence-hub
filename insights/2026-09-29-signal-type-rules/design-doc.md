# Signal 分类别信息规则 v1

状态：设计稿／待确认实施 · 日期：2026-09-29 · 对象：信息提取、候选审核和公开发布

## 1. 目标与现状

**[设计决定] 一条 Signal 是否完整，应取决于该类事件能否被准确说明和追溯，而不是所有字段是否被强行填满。采用共同必填＋类别必填；人物和组织按真实事件角色关联。**

[事实] 当前 Seed 有 15 个唯一 `type` 枚举，领域 `topics` 可多选；人工发布通道仍统一检查日期、组织、人物、领域，并未保存事件类型。公开读取也拒绝空人物／组织数组。[S1][S2][S3][S4]

[事实] 本批 39 条新候选中，28 条已获确认并转入本地正式 Seed，11 条仍待补：9 条缺人物、2 条缺组织。这些是旧四项口径的缺项，不等于事件事实一定不完整。[S5]

目标：覆盖全部 15 类；每类有可执行的最小完整条件；明确未知与不适用；消除编造关联人物的激励；仍由管理员确认发布。

非目标：本次不改代码、生产门禁或数据，不重新发布 11 条，不执行数据库迁移，也不新增收费模型调用。

## 2. 方案与取舍

| 方案                | 完整性定义                                 | 收益                                           | 代价与失效模式                                      |
| ------------------- | ------------------------------------------ | ---------------------------------------------- | --------------------------------------------------- |
| A：保持统一四项     | 所有事件必须有日期、人物、组织、领域       | 延续现行人工发布实现，变更最小                 | 机构署名公告无具名人物也会被阻断，易诱导用 CEO 补位 |
| B：分类必填（采用） | 共同信息＋各类事件核心事实；实体按角色关联 | 适合政策、研究、融资等不同事件，能解释具体缺项 | 需统一类型持久化及前后端校验，旧记录要明确兼容      |
| C：只要求正文与来源 | 编辑自行判断完整性                         | 最容易接纳不同内容，字段负担少                 | 不能稳定判断交易阶段、专利身份、研究归属等关键缺项  |

采用 B，但不是“AI 自行宣布不适用就自动发布”。字段状态和角色需有依据；发布仍需人工确认。信息越多不是必然越好，无法证明的姓名不应加入。

## 3. 所有类别共同必填

| 信息           | 规则                                                                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 标题           | 1–80 个 Unicode 字符，准确表达主体＋事件，不把计划、指控写为既成事实                                                                                                                                          |
| 摘要           | 1–500 个 Unicode 字符；说明发生什么、当前阶段和关键限制，不包含模型思考过程                                                                                                                                   |
| 唯一类型       | 从现有 15 类中选一项；不得为通过校验而换类，不新增 `editorial` 作为事件类型                                                                                                                                   |
| 领域           | 至少一个启用的规范 Topic，可多选、去重；新写入目标上限沿用人工通道的 5 项，不追溯截断旧记录                                                                                                                   |
| 事件日期       | 至少日精度；说明是发生、公告、论文发表、签约或正式生效日期。未来计划的 Signal 用已发生的公告日，目标日期另存；不得拿采集日代替                                                                                |
| 采集时间       | 系统记录，与事件日分开；日期事实有冲突时待核对，不猜测时分秒                                                                                                                                                  |
| 可追溯依据     | 至少一项可核对的原始证据及其定位，公开来源保留原始 URL。私有资料保留内部资料 ID、版本和片段位置，仅供候选和后台核对；公开事实仍需公开佐证，不能仅凭字段齐全或通用确认按钮公开私有事实。纯 AI 总结不是独立来源 |
| 核心主体及行为 | 明确谁／什么发生了什么；依类型可以是组织、人物、署名团队、产品、项目、技术或专利，不能完全匿名且无可识别对象                                                                                                  |
| 事实状态       | 明确已发生／拟议／签约待交割／逐步开放／指控／研究估算等适用状态；标题、摘要与状态一致                                                                                                                        |
| 审核决定       | 核心必填和适用的条件必填均满足后，由管理员确认；AI 只能准备材料，不能代替确认                                                                                                                                 |

原文已有具名参与者且与核心事件直接相关时，应保留其姓名和角色；尤其核心事实明确归属其作者、发明人、发现者、任职或获奖身份时，姓名和准确角色转为条件必填。仅“同一公司任职”不足以关联。原文不具名时不能自动代入现任 CEO、首席科学家或部门负责人。

来源记录最低包括来源主体、具体页面／文档、发布日期或“未核实”标记、核心断言定位及来源角色；来源发表时间不替代事件日。公司公告可以证明“公司宣布”，不自动证明性能经过独立复测。

评分不作为通用事实完整性的门槛：`confidence` 仅表示新闻可信程度；`importance`、`novelty` 有评估时才填，不把未知写成 0。不恢复 `strength`。现有 Seed Schema 仍要求三项评分，此处并未修改该约束；旧值保留，未来存储调整另做。[S1][S4]

## 4. 每个类别的最小信息集

下表内容叠加第 3 节。**“条件必填”指条件满足时必须有真实值或规定的披露状态，并不是任意可跳过。未公开仅可用于表内允许的非核心明细；不能替代事件主体、核心行为、日期或依据。**

| 唯一类型              | 事件核心必填                                                                                                                       | 条件必填与非阻断明细                                                                                                             | 人物／组织规则                                                                                                                |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `research` 研究       | 研究题目或对象；主要结论；可归属的作者／正式署名团队或机构；论文、报告或研究原文定位；结果成熟状态（预印本、同行评议、机构分析等） | 有性能／因果／数值结论时补实验或分析范围、基线／口径和限制；无原文支持不得泛化。DOI、代码和数据集按是否存在填写                  | 至少具名作者或可识别署名主体之一。具名作者研究不强制有组织；有明确作者单位或机构研究角色时关联。署名团队不能伪装成一个 person |
| `product` 产品        | 产品／服务／版本；发布或变更主体；核心变化；可用状态                                                                               | 涉及购买、接入或部署时写开放范围／获取方式；宣布价格或性能时写单位、条件、基线；未披露价格可留空                                 | 发布组织、维护项目或个人开发者至少一种可识别主体；不强制发言人姓名                                                            |
| `funding` 融资        | 融资或上市主体；融资方式／轮次或上市市场；事件阶段（计划、签约、完成、上市等）                                                     | 已披露金额写数值、币种及口径；投资方、估值、资金用途未披露时明确标记，不编造。IPO 必须有交易所及上市阶段依据，拟上市不能写已上市 | 融资企业／机构必填；已披露投资方以投资角色关联；高管或发言人非普遍必填                                                        |
| `acquisition` 收购    | 收购方＋标的；收购范围（股权、资产、业务等）；交易阶段                                                                             | 已披露对价写币种、现金／股票等方式；附带监管、股东批准或交割条件时必须说明；未披露价格不阻断                                     | 双方核心主体必填，可为机构或有证据的个人收购方；人物不是普遍必填，不能把签约写成交割                                          |
| `hiring` 人才         | 招聘／裁员／团队流动主体；动作；岗位／团队／人群范围；已宣布还是已实施                                                             | 报道人数时写数量口径和时间范围；按个人讲述的流动必须具名；正式职位任免以 `people` 为主                                           | 雇主／用人组织必填；集体招聘、裁员不强制列个人姓名，不公开无必要的员工身份                                                    |
| `policy` 政策         | 倡议／表态／战略名称或核心主张；发起／发布／签署方；适用对象或地域；当前阶段                                                       | 涉及联名时核实签署范围；只公开部分签署方时标明名单不完整。国家间倡议需识别发布机关或有证据的领导人／代表，不强制猜测执行部门     | 至少机构或具名倡议／发布主体；机构声明可无人物。国家名称可描述参与范围，不冒充已登记的执行机构                                |
| `technology` 技术     | 技术或系统；研发／实施主体；具体进展；成熟度（概念、实验室、试点、量产等）                                                         | 存在提升幅度时写指标、基线、测量条件；部署或可量产结论必须有对应证据                                                             | 组织、个人或可识别项目／团队至少一种；机构技术进展不强制具名负责人                                                            |
| `market` 市场         | 市场／企业／行业对象；指标或观察结果；统计期间；覆盖范围；数据／分析来源                                                           | 金额须币种、指标须单位；增长率须比较基期，预测须预测期及假设；无数值时必须有具体可追溯的市场事件，不能只写“发展迅速”             | 涉及某企业时关联；行业总体统计可无具体公司和人物，不能把统计发布媒体自动当作行业参与者                                        |
| `people` 人物         | 至少一个人物姓名及可核对身份；职务／观点／成就／任免等具体事件；角色或身份变化                                                     | 任免须说明新旧角色、所属组织和宣布／生效状态；观点须本人原话或可靠转述；同名歧义必须先解决                                       | 人物必填。任免、公司职务类组织必填；独立研究者的个人观点、获奖等不强制雇主                                                    |
| `open_source` 开源    | 项目／模型／数据集及版本；发布／维护主体；可访问发布入口；实际开放的内容与许可状态                                                 | 有许可证须定位文件／版本；无许可标明“公开可见、许可未明确”，不可宣称允许复用。仅开放权重须准确标注，不宣称训练代码／数据已开源   | 组织、具名维护者或可识别项目团队至少一种；个人项目可无公司，团队项目可无个人姓名                                              |
| `security` 安全       | 受影响产品／系统／组织之一；安全问题或事件；发生／披露日期性质；发现者／披露者或证据来源；事实确认程度；影响或风险范围             | 漏洞编号、影响版本、受影响人数、攻击者、修复情况按披露填写；未公开可明确注明。起诉、指控、疑似攻击不可写成认定事实               | 组织按受影响方、披露方等真实角色关联；人物通常非必填；不猜测受害者身份或攻击者，不公开敏感细节                                |
| `patent` 专利         | 专利名称；申请号／公开号等可核对编号；司法辖区；申请人；当前程序状态；核心技术主张                                                 | 有发明人公开名单时关联；有申请日、公开日、授权日则分别记录。只知道申请意向却无可核对登记时，不能写成已获专利                     | 申请人必填，可为组织或个人；不能将发明人和申请人混同；若申请人为个人，其姓名必填                                              |
| `partnership` 合作    | 至少两个明确合作方；各方角色；合作事项；协议／试点／实施等阶段                                                                     | 有期限、规模、投入、排他条款或交付目标时注明；合作愿景不能写成已交付结果                                                         | 至少两方真实主体，通常是组织，也可有明确个人／项目；不强制双方高管姓名；单方“采用某产品”不自动证明双边合作                    |
| `regulation` 监管     | 提案／法律／标准／执法事项；有权提出、制定或执行的机构；辖区／适用对象；法律或程序阶段；关键要求／措施                             | 有案号、标准号、正式文件号时必须引用；提案、发布、生效、起诉、裁判等日期分别保留。未定生效日不得猜测                             | 监管／立法／司法／有权标准机构必填；人物非普遍必填；有管辖效果的措施与一般政策表态分开                                        |
| `supply_chain` 供应链 | 芯片／材料／制造／算力设施等对象；参与企业／机构；产能、供货、制造、运输等具体变化；供应链环节；计划或实际状态                     | 有产量、产能、交付量、价格、地区或时间表时写口径；扩产规划不能算现有产能，订单不能算已交货                                       | 至少一个实际参与组织；人物非普遍必填。行业整体供需测算而非具体参与者变化可归 `market`                                         |

## 5. 唯一类型如何判断

按“本条最主要的新事实”分类，不按所属领域、信息来源或是否容易补齐决定。类型只选一个，相关主题放进多个 `topics`。

- `policy` / `regulation`：一般政策方向、倡议、官方表态用 policy；具体规则提案、法律／强制标准、合规限制、执法程序用 regulation。法案还在提案阶段也可归 regulation，但必须明确未生效。
- `research` / `technology`：新论文、报告、实验或分析结论用 research；具体工程系统或技术路线的研发／实施进展用 technology。研究里提到产品，不自动变成 product。
- `product` / `open_source`：新增可使用产品／服务能力为主用 product；代码、权重、数据等开放发布及许可变化为主用 open_source。不给同一发布人为拆出两条重复 Signal。
- `market` / `supply_chain`：财报、市场规模、价格指数、份额或总体供需判断用 market；具体企业的产能、供货、制造或交付变化用 supply_chain。按本条正文主张判断，不能所有晶圆厂财报都叫 supply_chain。
- `funding` / `acquisition`：企业融资、配售、IPO、非控制性投资用 funding；取得控制权或明确资产／业务收购用 acquisition。不可仅按“有金额”分类。
- `hiring` / `people`：组织招聘、裁员、团队结构性流动用 hiring；具体个人任免、身份、公开观点与成就用 people。
- `security` / `policy` / `regulation`：漏洞、攻击、滥用或事故披露用 security；防护倡议／政策建议为主用 policy；强制监管或执法为主用 regulation。安全机构署名不决定类别，现有蒸馏公告需要按正文主张重审。
- `partnership` / 其他：新合作关系和双方职责是核心才用 partnership；已经存在的合作只是产品发布背景时，按产品等实际新事实分类。

若两项独立事件具有不同时间、主体行为和独立来源，可分别成 Signal；否则保留一条，摘要说明次要信息。多来源佐证同一事件不等于多个 Signal。

## 6. 缺项状态与发布判定

拟为每个受规则管理的字段记录以下状态。这是待实现的审核元数据，不是当前 Schema 已支持的字段。

| 状态             | 含义                                           | 发布影响                                               |
| ---------------- | ---------------------------------------------- | ------------------------------------------------------ |
| `present`        | 有明确值及依据                                 | 满足对应必填要求                                       |
| `undisclosed`    | 已核对来源，确实未披露该非核心明细，并记录说明 | 仅允许表内金额、发言人等非核心明细；不能替代主体或依据 |
| `not_applicable` | 此类事件不要求该字段，记录判定理由             | 不阻断；不能由任意客户端字符串绕过类型规则             |
| `unverified`     | 提取到线索但尚未证实或存在冲突                 | 核心项阻断；可选项可不公开该值并保留待核实记录         |
| `missing`        | 应有但尚未取得                                 | 核心项或适用的条件必填项阻断                           |

“搜索没找到”不等于 `undisclosed`；“没有人物”也不等于 `not_applicable`。例如人物任命的姓名缺失是 missing，而无具名发言人的机构公告可以没有 person。

拟议判定顺序：共同字段 → 类型核心字段 → 条件必填 → 来源与字段一致性 → 明确展示风险／缺项 → 管理员确认。任一核心项不合格则待补；可选项没有公开值但不影响核心事实时，可进入待确认。通过规则不自动改变发布状态。

界面保持“尽量自动填好，管理员核对后一次确认”；有缺项才提供补充入口，不让用户手工编写 JSON、实体 ID 或核验签名。

## 7. 来源、组织、人物的关联边界

1. **来源与实体是不同角色，不是永远互斥的身份。** 来源负责“信息从哪里来”；实体关系负责“谁在事件中做了什么”。有独立依据时，同一个机构可以兼任来源与研究机构／监管发布方，必须写明角色。研究类的署名团队／机构必须被作品明确列为作者或研究责任主体，刊载平台和被引用对象不能代替作者。
2. ECB 博客上有作者，不等于 ECB 背书作者全部结论；可按研究作者建立 Signal，有材料证明作者单位或机构研究角色时再关联 ECB。仅刊载这一事实不足以推出其为业务实施方。
3. SemiAnalysis、新闻媒体与转载平台仍按本项目要求作为来源，不因为文章发布在其网站就登记为相关公司。被研究的 NVIDIA、Intel 等可按“研究对象”关联，不能写成研究作者。
4. “研究作者”“发言人”“研究对象”“发布机构”“签署方”“拟任高管”“受影响方”不能混写；推测的关联不进入正式实体关系。
5. 人工确认的名字不自动获得数据库实体 ID；同名实体合并须另行核对。私人导入材料和原始引用不因确认发布而自动公开。[S4]

## 8. 对当前 11 条待补的影响

## 9. 如何接入现有系统

[事实] 人工内容严格白名单没有 `type`，读取时硬编码为 `editorial`，统一公开模型因此显示 `type: null`。不补类型存储，仅放宽人物判断，会造成不同入口口径冲突。[S2][S3][S4]

[事实] 默认 AI 提示词以及旧证据合格发布 reader 也要求人物；旧设计明确“至少一个独立 Person ID”。人工发布目前可没有公开来源链接，且其读取将 `captured_at` 填为发布时间。因此分类型人物规则、后台证据门槛、准确采集时间都是实际行为变更，不是现行实现的描述。[S7][S8]

拟分阶段实施：

1. 确认本规则替代全类别“人物＋组织”硬要求的范围；先定义单一服务端规则函数和机器可读类别表，覆盖全部 15 类及缺项解释。
2. 增加版本化审核材料：事件 `type`、类型明细、角色、字段依据与状态、`rulesVersion`。它们是新字段设计，不可直接塞入现有严格 Seed 或人工内容 Schema。原 AI 候选和证据不被覆写。
3. 新规则版本下的 AI 提取／核验提示词、手工补充、后台预览、写入门禁和公开读取共用契约；不能只改表单。先为新人工确认通道及编辑复审接入，旧 `source_evidence` 签名／合格发布协议保持原条件，若需升级必须独立做协议和 reader 兼容设计，不得借本规则伪造其发表资格。旧数据仍按原版本读取，旧无类型记录不推断归类，无法恢复的采集时间不补造，不自动撤下或升级资格。
4. 先只读评估现有记录，输出分类变化／缺项差异；采用新规则重新发布必须明确确认并保留旧修订。需要的数据库约束或角色变更另行设计、审批和核验，本批不执行。
5. 验证列表、详情、搜索、资源与雷达能处理合法无人物／无组织的记录；允许空关系不等于补造热度或评分。新规则写入可关闭，已发布的合法新版本仍须可读，不能用回滚旧 reader 把它们读丢。

最低验收：15 类各有完整／核心缺项样例；机构公告无人物可待确认；人物类无姓名必拒；独立作者研究无组织可待确认；未披露金额不伪造；提案／签约／交割阶段不混淆；不得更换类型绕过必填；原文可追溯；旧版本读取不变；重复确认幂等、撤回仍有效。

## 10. 风险、反面观点与自评入口

| 风险／反对意见               | 缓解                                                                           |
| ---------------------------- | ------------------------------------------------------------------------------ |
| 不强制人物会使资源图谱更稀疏 | 接受真实空缺；有证据的具名人物优先提取，覆盖率可监测但不以凑数换关系           |
| 改类别逃避难以补齐的核心字段 | 类别绑定核心新事实、正文和来源，后端统一复核；变更留下规则版本及审核记录       |
| AI 滥用“未披露／不适用”      | 类型规则限制可用字段与原因；主体、事件和证据不能这样豁免；人工只确认不代填事实 |
| 稿件有数字却没有口径         | 相关条件字段转为必填；不满足时删去不可靠的数值主张或保留待补，不能自动补算     |
| 新规则对已发布旧内容造成误伤 | 版本化、只读差异审计和明确确认；不自动撤回、不篡改历史                         |
| 前后端或写入／读取校验不一致 | 同源规则及全链路回归；不能只改 UI。缺少分类型字段存储是实现前置阻塞            |

当前没有性能实验或生产部署结论；按类别判断是单条有限字段校验，性能风险预计低，但批量重评应分页、只读先行，避免把设计估算当实测。

开放决定：用户确认是否实施此按类门禁；结构化明细的具体 Schema／迁移方式由实现阶段确定。自评与独立审查见 [review.md](review.md)。
