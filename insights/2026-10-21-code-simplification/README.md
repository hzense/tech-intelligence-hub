## 结论与边界

[事实] 基线共 195,539 行源码，其中测试 101,196 行，非测试 94,343 行；包含注释与空行，不含依赖、文档、内容资料及 JSON/YAML 配置。统计脚本：[analysis/count-code.mjs](analysis/count-code.mjs)。

[推断] 大量代码不能仅凭行数判断多余。本轮选择运行时无引用的旧适配器，以及输出可以逐字验证的重复定义；不删历史数据库迁移、不改安全校验、发布规则、费用、原请求恢复或数据库数据。

同口径结果：源码总量 **195,539 → 192,316 行，减少 3,223 行（1.65%）**；非测试代码 **94,343 → 91,270 行，减少 3,073 行（3.26%）**。测试代码净减 150 行，来自退役组件专属用例及混合浏览器用例中失效入口的清理，现役请求身份／历史发布覆盖保留。文件数 838 → 834；本目录说明与统计脚本不计入应用源码口径。

## 方案取舍与风险

另一种方案是整体下线独立核验、补证与受限发布。它可能减量更多，但这些模块仍由 API、历史页面和发布表单调用，会改变功能与数据兼容性，因此不在本轮执行。也不把不同事务包装强行统一：它们的未知提交、连接释放和错误映射并不一致。

最主要风险是把测试专用引用误判为未使用，或在默认属性中漏掉安全字段。缓解方式是检查路由与动态加载、固定完整契约散列，并执行当前页面回归和真实 PostgreSQL 校验。反面观点：精简静态清单主要降低维护成本，并不证明运行时更快或数据库流量更低；本轮不宣称这类收益。
