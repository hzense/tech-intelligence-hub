# Signal-first 五项实施

状态：开发中 · 2026-09-26 · 基线 main 54c402b

## 1. 背景与目标

[事实] 详情页修复已上线，后台生成和管理员确认发布已可用；现有导航仍包含日报、周报、洞察、专题。`PROGRESS.md` 留有过去的未上线快照。

目标是让已发布信号成为统一的前台输入，并补齐定时生产的配置和持久执行入口。验收覆盖筛选 URL、当前/历史隔离、撤回后各入口一致、任务幂等和费用边界。

## 2. 范围与边界

1. 整理当前进展和三份既有验收记录，保留历史结论，追加取代说明。
2. 信号交集筛选、分页、分组及人物组织跳转；旧信号显式历史入口。
3. 雷达首页：事件时间窗口、最多十条热点、评分分项和样本不足提示。
4. 资源由公开关联构建，按近期信号数排序；人物与组织的共同出现不冒充任职关系。
5. 管理员配置来源/计划、持久运行和专题周度/手动分析；生成后仍人工确认公开。

非目标：不改生产密钥、自动付费运行、切换旧数据权威、伪造人物、重启恢复演练或实现 OCR。

## 3. 约束和假设

- [事实] 新管理员确认记录没有可信热度/重要度评分；缺失分项展示缺失，不生成假精度。
- [事实] 现有公开读模型尚不能证明来源采集覆盖率和跨来源事件消歧；趋势显示统计变化，不将低覆盖解释为真实行业趋势。
- [假设] 当前公开规模适合有界服务端聚合；保留读取上限，超限/读取失败报错而不回退私有或旧数据。
- 定时功能默认关闭，新数据库对象和最小权限须独立审批；新 AI 任务需要预算预留和已配置的阶段 Profile。

## 4. 方案比较

| 方案                               | 优点                                     | 代价                                 |
| ---------------------------------- | ---------------------------------------- | ------------------------------------ |
| 先整体切换数据库权威再重做前台     | 数据体系单一                             | 必须先补齐旧人物与迁移，阻塞可用功能 |
| 复用公开读门面，显式区分当前与历史 | 保留旧 URL，当前发布立即可见，不扩大 ACL | 需清楚标注历史，不能宣称全量迁移     |

采用第二种。统计和新洞察只消费当前正式记录；历史归档可查，不补造关系凑数。

## 5. 实现与验收

- 服务端统一读取；动态页面不用静态 fallback，避免再次触发 DYNAMIC_SERVER_USAGE。
- 筛选、分组、分页共享同一集合；未知参数有界处理，日期按 UTC，正文由 React 转义。
- 任务先持久化再派发；并发/重复触发复用编号，远程结果未知不得自动二次付费。
- 专题输入冻结公开信号版本，结果必须保留引用；私有候选和上传原件不能进入公开洞察。
- 测试纯计算边界、鉴权/Origin、任务幂等、预算、引用、当前版本撤回，再进行生产构建和浏览器桌面/移动验收。

## 6. 发布与风险

代码、迁移准备、生产配置、真实收费验收分别报告。新增存储默认关闭且有明确未配置状态；保持现有套餐，不以定时请求长时间等待 AI。

主要风险：历史内容在默认列表减少；热榜初期不足十条；来源网页不可抓取；预算耗尽或模型结果不满足结构；新的投影缺乏撤回即时核对会泄漏过期内容。对应措施为历史入口、诚实空态、安全抓取、失败不自动重试收费、公开读取复核依赖。

## 7. 自评

问题、范围、兼容和安全边界明确；可靠性、运维与成本须以本批测试及后续生产验收确认。最强反对意见是当前信号少，改首页会显得空：仍选择真实展示，不使用旧信号或虚构评分填满首页。
