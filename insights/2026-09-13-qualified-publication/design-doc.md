# 私有已记录资格检查与原子发表设计

状态：本地实现及验证完成 · 2026-09-13 · 用途：本批代码与 PR 评审 · 非生产授权

## 1. 背景与问题

[事实] 本批开始前，控制入口和 Outbox 转换各自存在事务边界，尚未与版本组装共同提交。`docs/SIGNAL_PUBLICATION_CONTROLS.md:58` 明确禁止先提交门禁再调用独立转换入口。

[事实] 3.0.0 哈希包含 version；旧 writer 的 pending 人物／组织边提交后已封存。不能复制旧哈希，也不能直接改写旧边完成审核。依据：`packages/content/src/signal-v3.ts:103`、`docs/SIGNAL_VERSION_IMMUTABILITY.md:21`。

## 2. 目标与非目标

目标：从已存在的封存候选复制新版本；锁定并检查当前已记录资格；在同事务写完整版本、四类边、head、Outbox、绑定回执；任何失败无残留；同键重试不产生新修订。

非目标：AI 核验、人物消歧、私有上传、完整事实覆盖与独立来源判定、认证 API、生产角色、安全撤回服务、公开 Reader、搜索消费者、生产迁移。旧站继续读取旧数据。

## 3. 约束与假设

- [假设] 本轮按已确认的增量路线完成私有事务核心，暂不开放应用调用；以无新增路由／角色授权及原生越权回归验证边界。
- [事实] 旧迁移不改，只追加回执绑定及精确 catalog 契约；不会重新定义 3.0.0 内容字段。
- [假设] 数据库里的 verified 是受信任核验路径的记录，不是本服务重新阅读原文所得事实；独立自动核验及持续公开资格仍待实现。
- [推断] 不需要另建“当前资格”缓存表；直接在事务中锁定当前依赖可避免多一个需要同步的权威状态。

## 4. 候选方案对比

| 方案                                                 | 本轮能力                                         | 主要成本与限制                                                   |
| ---------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| 发布既有封存版本，不复制                             | 可同事务检查资格并更新 head／Outbox              | 无法为本次组装与回执建立同事务新版本边界；后续仍需新版本组装服务 |
| 从已记录合格的封存候选克隆新版本                     | 复用当前数据与封存保护，检查、组装、回执共同提交 | 多保留一个内容快照；pending 候选仍不能自动升级                   |
| 增加候选审核决策、断言核验与完整生成结果模型后再发表 | 可以承接真实自动核验产物                         | 本批同时扩展内容权威、认证、AI 生成与生命周期，交付范围明显扩大  |

## 5. 推荐方案

选择克隆方案，先完成可验证的事务核心。来源版本与发表版本是不同快照，事件日期／采集日期不变；保留来源版本和原始 run 的绑定，明确放弃本轮完成 pending 升级流程。

## 6. 详细设计

请求只含稳定请求键、Signal／来源版本／目标版本、前置发布修订、原因码及 run／lease owner／fencing。不能传正文或 authorized／verified 标记。

同一短事务：请求键 advisory lock → 查不可变回执 → 控制总开关／任务／授权／run → Signal／head／版本／身份 → Source／Evidence／Entity／档案／Topic → 已记录资格 → 再检查租约 → 组装新版本和四类边 → Outbox／head／绑定回执 → 执行延迟约束 → 最终租约检查 → COMMIT。每张依赖表内部按主键 C 排序。

[推断] 永久绑定回执的语义指纹需包含 source、target、run、Signal、前置修订和原因码；不包含租约 owner/token，允许同一运行合法重领后继续同一操作。旧已提交回执可返回历史结果，不能凭它恢复 head 或宣称现在仍可公开。

来源版本日期在数据库内先校验有限值、四位年份和毫秒精度，避免 pg 驱动截断微秒后“验证”失真的哈希。克隆仅改变版本与相应哈希。所有复制人物／组织边须有支持证据及已记录 verified 状态；支持／背景证据及其来源当前有效、人物／组织档案类型及 active 状态匹配、Topic 允许运行且未归档。身份依据版本的未解决反证同样阻断；已 rejected 反证可保留历史，不视为支持或要求其来源仍启用。

资格检查覆盖记录的依赖，不推断任职、CEO 或新雇主；仅靠 reporter 等角色词黑名单也不能证明行业参与，应把该限制留在真实核验契约中。

## 7. 迁移与发布

先本地开发及隔离 PostgreSQL 集成，再按用户要求提交 PR。PR CI、合并、生产迁移、角色配置和公开读取切换分别确认。没有生产入口时无需切换旧站或创建云资源。回滚代码不删除新回执或历史版本；生产 DDL 策略须在真正维护前另审。

## 8. 反面观点、风险与缓解

- 最大反对意见：继续追加私有基础会推迟用户可见功能。[推断] 本批提供可被后续审核／生成结果路径调用的单事务核心，但不能把它算作网站已改版；下一阶段应接核验产物和受限服务，而不是继续无限增加日志。
- 租约可能在依赖锁或写入等待时过期：最后执行约束与重新取数据库时钟；失败整笔回滚。不保证 COMMIT 磁盘持久化耗时也小于租约期限。
- 上线后来源撤销却仍被索引展示：本批没有公开 Reader，不开放权限；后续必须实现协调撤回和读取时资格检查。
- 可信 owner 直接 SQL 可绕过应用资格或改 DDL：明确受信任管理边界，不给 Worker／Runtime 新授权。
- 十倍依赖量：每个投影集合上限 256，超限拒绝；短事务不跨模型／网络。此上限是工程保护，不是性能 SLO；生产规模基准未核验。
- 已核验状态不等于事实正确：证据独立性、断言覆盖、私密材料风险必须由下一层真实核验解决，禁止将私有回执当公开资格票据。
- 六个月失败预演：[推断] 把 recorded 误当实际核验，会使不真实内容取得私有 published；只看旧 Outbox 而不复核当前资格，会使撤销内容继续展示；反复超时后换请求键，会把未知提交误做新操作。对应缓解分别为禁止本批公开、后续协调撤回／Reader 门禁、永久回执与同键恢复协议。
- 删减测试：[推断] 本批没有建立独立“当前资格”表，因为它只会引入第二份需同步的状态。保留绑定回执是必要的：旧 Outbox 指纹不含来源版本和 run，无法识别换运行或换候选的伪重试；既有 Outbox 仍负责发布修订账本，两者职责不同。

## 9. 开放问题与自评

开放：pending 到已记录合格候选的受控核验路径、角色权限、独立安全撤回、证据失效协调、公开读取／真实消费者、线上时延和吞吐评测。

自评采用 fable-insight 的 design-review rubric，结论仅适用于本批私有实现；[实际验证记录](../../docs/SIGNAL_QUALIFIED_PUBLICATION.md#6-验证与交付状态)不替代将来的 CI 或生产验收。
