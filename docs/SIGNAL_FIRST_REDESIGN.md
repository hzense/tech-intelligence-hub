# HZense v2：以信号为核心的网站重构设计

**版本：** 0.3

**日期：** 2026-09-12

**状态：** 根据操作者提出的四项产品方向及批量资料导入补充要求形成的设计稿；尚未实施、迁移或上线。

**范围：** 公开网站的信息架构、人物与组织关系、AI 生产后台、评分与聚合、数据权威切换及迁移验收。

本文是新版产品的详细设计入口。[DESIGN.md](DESIGN.md) 保存产品总纲，[AI 自主 Signal 专项设计](AUTONOMOUS_SIGNAL_PIPELINE.md) 保存采集、批量导入、核验、发布与运行技术契约，[PROGRESS.md](PROGRESS.md) 区分设计与实施；[INFORMATION_MODEL.md 第 40 节](INFORMATION_MODEL.md#40-postgresql-物理数据库设计) 仍描述已实现的物理数据库，不因本提案而自动改变。

## 1. 产品重定位与决策边界

HZense 从“按日报、周报、文章分类的网站”转为“持续发现事件、连接产业人物、判断领域趋势的技术情报平台”。

> 来源资料 → 信号事实与证据 → 人物／组织关系 → 趋势、热点与专题洞察

信号是唯一的新增情报事实入口；专题洞察是对信号的分析产品，资源是信号关联的实体目录，雷达是这些数据的趋势与热点视图。三者不是彼此独立的内容录入系统。

### 1.1 已明确的产品方向

| 操作者要求               | 新版设计                                                                       |
| ------------------------ | ------------------------------------------------------------------------------ |
| 不再需要日报和周报       | 从主导航和新增内容生产中移除；旧内容只读归档，不作为新洞察必经输入             |
| 信号至少关联一位业界人物 | 新版公开信号必须有至少一条可核查的事件—人物关系，可关联多人                    |
| AI 自动采集，后台配置    | 网页配置来源、模型、频率、领域与预算，任务在服务端持续运行                     |
| 手动批量上传文档及超链接 | 后台统一导入中心，提交后触发 AI 信号提取、核验、人物关联及发布；可查看逐项结果 |
| 信号多维聚合             | 时间、领域、趋势、关键词分组；可组合人物、组织、事件类型筛选                   |
| 合并洞察与专题           | 一个“专题洞察”入口，长期专题下保存多期、可引用的深度洞察                       |
| 每周深入洞察，可手动启动 | 每周调度与后台立即运行共用执行器、证据与预算规则                               |
| 雷达首页，热点 TOP 10    | 进入网站即看到领域趋势和最多十条去重热点，展示评分依据                         |
| 资源自动更新，活跃者优先 | 根据已发布信号更新组织与人物，按近期独立事件活跃度排序                         |

“登陆网站后”按“打开网站后”理解：公众阅读不要求注册或登录，只有管理后台需要身份验证。本版不额外引入会员、评论、订阅支付或个性化推荐。

### 1.2 默认值与发布策略

本文的评分权重、窗口、采集频率和数量阈值均为**建议的首版参数**，需要配置版本、测试和真实样本校准，不是已验证的行业标准。

自动采集与自动公开是两个独立开关。沿用 [初版专项契约（b5a0045）](https://github.com/hzense/tech-intelligence-hub/blob/b5a0045f1c7e7591fe04d49409dd5148a10d87aa/docs/AUTONOMOUS_SIGNAL_PIPELINE.md) 已明确的产品方向：**Signal 三类入口（自动来源、文档上传、链接提交）默认 `auto_publish`，通过机器证据与人物规则后自动发表，无必经逐条人工审核。**“产品默认自动发布”不等于生产开关已启用；工程试运行和首次生产启用仍有各自的配置与验收。

- 生产能力支持 `auto_publish`、`review_required`、`preview_only` 三种策略，Signal 与专题洞察分别配置。
- 定时 Signal 沿用默认自动发表，不重新要求确认已有产品决定。手动导入提供“生成并发布”和“仅生成预览”；前者对本批选用 `auto_publish`，不修改其他计划的配置。新范围“专题洞察”的默认发表策略尚待确认，未明确配置前只生成预览，不擅自扩展 Signal 的自动发表授权。
- 工程试运行统一使用 `preview_only`。启用正式任务时必须明确记录所选策略；即使选择 `auto_publish`，证据、人物、隐私和时间校验也不能关闭。
- 人工审核是可选策略，不是所有自动任务必经步骤。机器校验失败进入补查／暂缓，管理员可以处理问题，但不能用“强制通过”伪造证据。

## 2. 信息架构

```text
HZense
├── 首页 · 雷达              /                      趋势与热点
├── 信号                     /signals               事实与证据探索
│   └── 信号详情             /signals/[id]
├── 专题洞察                 /topics                长期跟踪主题
│   ├── 专题主页             /topics/[id]
│   └── 洞察版本             /topics/[id]/editions/[version]
├── 资源                     /resources             默认组织目录
│   └── 组织／人物详情       /resources/[id]
├── 搜索                     /search                全站工具入口
└── 管理后台                 /admin                 独立受保护入口
```

主导航只有“雷达、信号、专题洞察、资源”，搜索作为全局工具；Logo 返回首页。桌面和移动导航使用同一份配置。首页不再先展示营销大标题、示意关系图或日报入口。

### 2.1 术语只保留一套含义

- **领域 Domain**：现有 Taxonomy 的一级技术领域，不再另建与 Taxonomy 不一致的四类 Radar 领域枚举。
- **专题 Topic**：持续跟踪的技术问题／方向，使用稳定 Topic ID，跨领域时可有多条映射。
- **洞察版本 Edition**：某专题在某个截止时间形成的一次深度分析，不是新的 Topic。
- **趋势 Trend**：领域／专题在指定统计窗口的变化状态，不是 AI 随意添加的标签。
- **关键词 Keyword**：事件文本中的规范化术语与别名，辅助发现，不取代正式 Taxonomy。
- **热点 Hotness**：可解释的当期信号排序，既不等于浏览量，也不等于长期战略价值。

## 3. 首页：雷达与热点

### 3.1 桌面布局

```text
Logo    雷达  信号  专题洞察  资源                       搜索  主题切换
当前技术态势                     趋势：本周对比上周 · 截止／更新状态
┌────────────────────────────────────────────────────────────┐
│ 各领域趋势：领域名 · 上升/平稳/下降/证据不足 · 事件数 · 小趋势图 │
│ 点击领域 → 对应领域的信号视图；展开查看统计依据与来源覆盖        │
└────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────┬──────────────────────┐
│ 热点信号 TOP 10 · 最近7天 ▾          │ 本周专题洞察         │
│ 01 标题 · 一句话变化                │ 专题 · 主要判断      │
│    事件时间 · 人物 · 组织 · 领域     │ 更新日期 · 证据数量  │
│    热点分 · 为什么上榜              │                      │
│ 02 ...                              │ 当前活跃组织         │
│ 查看全部信号 →                      │ 组织 · 近期事件数    │
└─────────────────────────────────────┴──────────────────────┘
```

首屏先回答“哪些领域在变化”和“现在最值得看什么”；趋势图不能挤走热点标题。移动端顺序为：紧凑状态栏 → 领域横向选择／趋势摘要 → 热点列表 → 专题洞察 → 活跃组织，不用不可阅读的大型关系网。

### 3.2 首页内容规则

- 热点榜默认最近 7 天，支持 24 小时／7 天／30 天；该控件只影响热点，不改变领域趋势的完整日比较窗口。趋势卡单独标明“最近 7 个完整日 vs 前 7 日”，各自显示截止时间和最后成功计算时间。
- TOP 10 按第 8 节评分排序；同一事件只占一个名次。全领域榜不暗中插入领域配额或人工置顶。
- 少于十个符合条件的事件时显示实际数量及原因，不拿旧消息、低质量内容补满十条。
- 每条热点有事件时间、至少一位人物、主要组织、领域和“为什么上榜”；可展开各评分分项。
- 领域趋势允许“证据不足”和“采集覆盖变化”；不显示未经计算的上升箭头。
- “本周专题洞察”展示已公开版本，标明分析截止时间；尚无本周版本时展示最后一期及其真实日期。
- 原有人工 Radar 历史快照保留为历史资料，不作为今天自动趋势的默认数据。

## 4. 信号：事实与关系的核心页面

### 4.1 列表与聚合

顶部提供搜索词、事件日期范围、领域、专题、趋势、关键词、人物、组织、信号类型。默认按事件发生时间倒序；可切换热点／重要度排序。

提供三种视图：

1. **紧凑列表**：标题、两行事实摘要、事件时间、人物／组织、领域、重要度、来源数量。
2. **时间线**：按事件日期分组；支持天／周／月，组头显示不同事件数。
3. **聚合视图**：按领域／趋势／关键词分组，显示组内事件数、变化和代表信号，并能展开列表。

这不只是添加筛选按钮：选择领域后再按关键词聚合，统计与列表必须基于同一筛选结果。不同维度取交集，同一维度多选取并集；组内去重，同一多领域事件可进入多个组，因此“各组之和”可能大于全局去重总数，界面明确说明。

示例 URL 契约（名称为设计建议）：

```text
/signals?range=7d&domain=artificial-intelligence&group=keyword&sort=hot
/signals?from=2026-08-01&to=2026-08-31&person=PERSON_ID&view=timeline
```

时间边界按页面所选时区展示，内部使用明确的半开区间；分页使用绑定筛选条件、排序版本及快照时间的游标，避免热榜刷新造成重复／漏项。返回浏览器后保留筛选和位置。无匹配、数据加载失败、尚未采集是三种不同空态。

趋势筛选取所选窗口截止时的专题趋势快照；多专题信号可以属于多个趋势组。未有合格快照则归入“未判定”，不把一个 Signal 自己等同于一条产业趋势。自定义历史窗口没有可用快照时明确降级，而非套用今天的趋势。

### 4.2 信号详情结构

1. 标题、事实摘要、类型和事件时间；采集／发表／更正时间作为独立元数据。
2. **发生了什么**：主体、动作、关键数字、完成／计划／传闻等事实性质。
3. **关键人物**：姓名、当时职务／组织、与本次事件的关系、证据链接；支持多人。
4. **为什么值得关注**：AI 研判、影响范围、前提与不确定性，明确区别于事实。
5. **原始证据**：精确来源页、发布时间、支持哪些断言、转载归属及必要的短摘录。
6. 相关组织、专题、前后事件与修订记录；热点评分及计算窗口。

不再把所有文本放进一个“为什么重要”长卡片。事实、解释、预测与待观察问题有清晰标识；“AI 生成／人工修订”与版本日期可见。

### 4.3 人物关联是发布约束

新版 `published` Signal 必须关联至少一个独立 Person ID；多个名字不能存成一段无法查询的字符串。每条关系包含：人物身份、事件关系类型、证据、有效日期／日期精度、核验状态。

关系类型例如：事件参与者、研究作者、公告发言人、项目负责人、政策签署人。仅当来源明确支持时才可标注。新闻报道的记者可以作为来源作者保存，但不自动满足“相关业界人物”的要求。

- 来源无人物 → 自动补查该事件的论文、公告、发布会或项目资料；仍无法核实则 `needs_person_evidence` 暂缓。
- 公司出现不等于 CEO 参与了该事件；不能批量给全部组织新闻附上 CEO 来满足数量要求。
- 同名人物按组织、职务时间、官网／ORCID 等公开标识消歧；不能仅按姓名合并。
- 人物身份或证据撤销后，所有依赖它的当前公开版本及待发表版本都须重新校验；失去最后一位合格人物的内容事务化更正／撤回，不在下游悄悄保留失效关系。
- 只保存与专业活动有关的公开身份信息，不采集私人联系方式、家庭情况或无关敏感信息。

这项要求会降低无人物公告的采集覆盖率，是本产品取舍的一部分。不能为了覆盖率虚构人物。

## 5. 专题洞察：长期主题与持续研判

### 5.1 合并方式

保留 `/topics` 作为“专题洞察”唯一目录。每个专题有一个长期主页，主页显示最新有效洞察、领域、核心问题、关键人物／组织、证据时间线和历史版本。

专题目录卡片显示：专题名、一句话最新判断、趋势、最新分析日期、证据信号数量及新增变化。按最近更新／领域／趋势筛选；没有深度报告的专题标记“跟踪中”，不伪装成已生成洞察。

专题和领域 ID 仍由现有 Taxonomy 管理。AI 可以发现候选聚类、更新已有专题；新概念先放入“候选专题”，通过去重及 Taxonomy 纳入流程后获得正式专题入口。不能由 AI 绕过现有 Taxonomy 权威创建不受控的平行 Topic 表。

### 5.2 一期洞察的正文

- 摘要与 3–5 个关键判断。
- 本期发生了什么变化，与上一版本相比有何不同。
- 支持证据：精确关联 Signal ID、版本及原始来源。
- 相反证据、反例、来源依赖和尚未确定的事项。
- 人物与组织：参与者、角色变化和竞争／协作关系。
- 趋势解释、可能影响及有条件的未来情景。
- 接下来观察什么：可以被未来信号验证或推翻的观察点。

“每周一次”是重新分析频率，不是新的周报产品。不创建按全站日期机械汇总的 Weekly 页面，也不让 Daily 成为输入前提。一个 Signal 可以被多个专题和多期洞察重复引用；旧日报的“一次消费”规则不适用。

### 5.3 调度与手动启动

建议默认每周一 07:30、`Europe/Berlin`，后台可修改时区和时间。周度证据窗口为本地前一周 `[周一 00:00, 本周一 00:00)`，运行时另存 `as_of` 和实际执行时间；DST 由时区规则处理，不把一周恒定写成 168 小时。

后台立即运行可指定专题、事件范围、分析截止时间、上下文回看范围和发布策略。触发前显示预估信号数量与预算，运行后返回固定任务 URL；关闭网页不影响执行。

建议首版生成门槛：至少 3 个不同的合格事件、2 个独立证据归属组，且自上次版本以来至少一个实质新增事件或已核实的重要更正。门槛是暂定质量参数，不能保证结论正确。单一重大事件可展示在 Signals，不强行扩写成“深度趋势报告”。

证据不足／输入未变化时记录 `no_material_update`，保留旧版及日期。历史上下文可使用旧信号，但新旧证据清楚区分；历史补录不伪装为本周新事件。外部检索发现新的事实时须先形成并核验 Signal，再冻结本次洞察输入，不能把无登记事实偷偷加进文章。

## 6. 资源：组织活跃度与关键人物

资源首页默认展示公司和机构，按第 8 节“近 30 天活跃度”排序。保留人物、产品、模型、论文等已有实体的检索和详情能力，不丢失旧资源链接。

组织卡片包含：名称、组织类型、领域、简要介绍、近 30 天不同事件数、最后事件时间，以及 1–3 位有依据的关键人物。更多人物在详情页展开；缺少公开依据时显示“人物资料待补充”，不自动虚构职位。

组织详情包含：

- 基本资料与官网、核验日期；来源归属不等同于组织主体。
- **当前关键人物**：姓名、职务、角色有效期与来源；历史任职单独折叠。
- 近期信号、事件时间线、关联专题洞察、活跃度变化。
- 相关产品／技术／论文和组织关系，延续已有资源逻辑。

组织来自已发布信号中的有据主体关系。候选里的组织可提前入内部消歧库，但不因被 AI 猜测出现就进入公开榜单。名称变化、收购、同名机构使用稳定 ID 与有据别名处理。

组织活跃度只统计该组织为事件主体／参与方的信号，背景提及不计分；不能通过人物现任职务反推其所有历史事件都属于新雇主。人物详情采用同一资源路由，展示其组织任职时间线及有证据的关联信号。

活跃表示“近期被本系统有效覆盖的活动较多”，不等于信誉、投资价值或正面评价。

### 7.2 信号流水线

```text
调度／后台启动 → 来源抓取（优先 RSS / API） ──┐
手动文档上传 → 私有存储与文件安全检查 ──────┤
批量超链接 → URL 校验与受限抓取 ───────────┘
  → 文档解析与规范 URL 去重
  → AI 提取独立事件、人物／组织、时间与断言
  → 历史事件匹配、人物消歧、来源独立性与交叉核验
  → 中文事实摘要、重要度理由、影响研判、领域／关键词
  → 发布资格检查
      ├── 缺人／冲突／无证据：有界补查 → 暂缓
      ├── preview_only：保存预览，不公开
      ├── review_required：审核后进入同一发布服务
      └── auto_publish：规则通过后进入发布服务
  → 不可变公开版本 + Outbox
  → 信号页面、搜索、首页趋势与热点、资源活跃度更新
```

建议普通来源每 6 小时采集一次，少数高频来源可单独设定；调度器只投递任务，所有长任务在持久化后台分步运行，不在用户打开网页时调用模型，也不要求操作者在本地运行脚本。

一份文档可拆出多个不同事件；同一事件的多篇报道合并证据，而不是多条 Signal。官方公告可支持“该组织宣布了 X”，不自动证明其宣传的效果或行业影响；普通媒体的关键事实默认要求两个独立来源，转载同稿算一个。争议事实需补查相关方回应和冲突证据，不能仅凭两个模型意见一致发表。

### 7.3 安全、持久化与费用

- 资料中的提示词、HTML、代码都视为不可信输入，不能改变系统规则、执行 SQL 或获得任意网络权限。
- 抓取遵守来源授权和访问限制，不绕过登录／付费墙；只公开所需事实、引用和简短摘要，原文按授权及保留期管理。
- 来源抓取、自定义模型 Endpoint 和重定向统一防 SSRF；拒绝私网、云元数据地址、URL 凭据及不允许的跨域密钥转发。
- 模型 API Key 只由服务器密钥系统／加密引用管理，后台保存后只显示掩码；原始文档、完整模型输入与任务日志默认受保护。
- **先创建 Run／Generation ID，再调用模型**；保存输入 Signal 版本集合、配置／提示词／模型版本、规则结果、输出、用量、费用、时间及操作者／调度身份。
- 专题正文和信号研判先持久化再供页面读取；刷新、关闭页面不重付费生成。相同输入指纹和配置复用已完成结果，明确“重新生成”才产生新尝试。
- 同一任务默认并发 1；调度幂等键、步骤 checkpoint、租约与 fencing token 防重复提交。网络／模型调用不占据长数据库事务。
- 失败重试有上限，建议补查最多三轮；认证失败暂停连接，预算耗尽暂停付费步骤，不降级跳过核验。
- 费用调用前原子预留、调用后结算，测试与重试也计费；配置模型单价及 token 上限，无价格时标为估算且需保守预算。实际费用以服务商账单为准。
- 调度保存 IANA 时区与下一次执行时间，展示接下来五次运行；重叠执行合并／跳过、停机后有界补跑，取消在发布事务前复查。
- 配置快照用于追溯，不覆盖当前安全开关：关闭自动发表／来源、改为预览或撤销模型连接，对运行中的后续步骤也生效。发表事务再次检查当前发布总开关、所选策略、任务取消、有效租约和来源／人物／证据资格，旧快照不能恢复已撤销权限。

### 7.4 文档与超链接批量导入（正式功能）

管理员可以主动提供资料，不必等待定时抓取。入口为 `/admin/imports`，文件与链接允许混合进入同一批次，经过同一套提取、核验、人物补证、去重和发布流程。

#### 操作界面

```text
资料导入                         查看历史批次
┌─────────────────────────────────────────────┐
│ 拖入文档 / 选择多个文件                      │
│ 批量链接：每行一个，也可粘贴单个 URL         │
└─────────────────────────────────────────────┘
待提交列表：类型 · 名称/域名 · 大小 · 校验状态 · 移除
处理配置：领域范围 · 语言 · AI Profile · 本批预算
来源信息：每项可补原始公开 URL、资料日期及说明
[仅生成预览]                      [生成并发布]
```

“上传”负责持久化输入，“生成并发布”是管理员对本批执行的显式操作；选中文件或拖入浏览器本身不立即发表。按钮旁明确提示会调用配置的 AI 服务并可能公开生成的 Signal，显示本批数量与预算。提交成功返回 `batchId` 并跳转固定详情页，不等待 AI 全部完成。

#### 文件、链接与限制

- 首版支持 PDF、DOCX、Markdown、TXT、HTML、CSV、XLSX，多选／拖拽与批量链接均纳入验收。旧 `.doc`、宏文件和压缩包不直接执行／展开，返回转换提示；不执行表格公式。
- 扫描 PDF、PNG／JPEG 的 OCR 是首版必需入口。解析能力与对应费用配置通过测试后才能使用；未配置时界面明确提示、该能力仍记为未完成，不以“可选功能”跳过最终验收。
- 表格保留 sheet／行列／单元格位置、表头及上下文，设置 sheet、行列、单元格和解析 token 上限；不能把缓存公式值冒充重新计算结果。OCR 低质量、数字歧义或表格上下文缺失时暂缓有关事实，不把空解析计作完成。
- 建议初始上限：单文件 25 MB，每批 20 个文件及 100 个链接，文件总量 200 MB，单文档 300 页。以上为待压测参数，由服务器强制执行，后台显示当前限制；超限项单独标识，不静默截断整批。
- 批量链接按行解析、去空行、规范化并显示输入错误。单链接可提交；文档中的链接只作为发现线索，有界抓取，不无限递归跟随，也不绕过来源准入与出口安全规则。
- 大文件通过受保护、短期且对象键限定的上传凭证进入私有对象存储；服务端校验实际大小、文件签名、内容哈希与归属。完成上传后才允许解析，不能仅凭浏览器声称上传完成启动任务。
- 文件名、MIME、HTML 和 Office 内部资源均不可信；解析隔离执行，限制内存、CPU、展开体积、页数与网络访问，不执行宏、脚本或外部引用。
- 上传中断可重试相应文件；**只有服务器已确认收到的内容**可以在关闭浏览器后继续处理。关闭网页不会取消已经提交的后台批次。

#### 从资料到 Signal

一份文档可以生成零条、一条或多条 Signal；多份文档／链接可以共同支持同一个事件。系统先保存文档、原始链接、规范链接、内容哈希和解析位置，再建立 `import_item → evidence → signal_version` 多对多关联，不能按文件数量机械生成同数量信号。

文档证据保留页码／段落，表格保留 sheet／单元格，OCR 保留原页／图像区域及识别质量，网页保留精确 URL 与内容位置；每个关键事实、人物关系和事件日期都有依据。用户填写的资料日期只是元数据建议，不能覆盖事件发生时间。历史材料允许生成历史事件，但不能因为今天上传就进入近期热点。

重复导入按三层处理：

1. 文件哈希／规范 URL 识别同一输入；同 URL 内容变化创建新的文档版本。
2. 按输入版本、解析器、配置与提示词指纹复用已成功解析／生成步骤，不因点两次按钮重新收费生成；相同哈希跨批引用须先验证访问权。
3. 按事件身份和公开版本检查去重；新证据关联已有 Signal，必要时生成更正版本，不再发表一个重复事件。并发批次由数据库约束及发布事务处理竞争，不只依赖 UI 禁用按钮。

重试产生新的 attempt 并引用原 batch/item/run ID；对于服务商已执行但响应丢失的模型调用不能保证绝对不重复计费，应先对账／标记未知状态，再有界重试并记录费用。发布侧仍须保证幂等。

#### 发布与私有资料边界

- “生成并发布”对符合规则的事件自动发布；缺人物、事实冲突、证据不足或涉及私有信息则补查／暂缓，并显示原因，不整批强行通过。
- 上传文件、文件名、本机路径、临时下载地址和运行日志默认私有，上传不等于授权公开原文；后台仅通过已配置且允许处理该类资料的模型连接执行，并提示资料会发送给该服务商。
- 公开 Signal 优先链接上传者提供且经核验的原始公开来源；没有公开链接时自动寻找公开佐证。默认只发表可由公开证据独立支持的事实与分析，不让私有附件中的独有信息混入摘要。
- 如果一条事实仅由未公开文档支持，进入 `needs_public_evidence`，可以补充公开链接后重试。直接公开原始文件或以其为唯一公开证据需要独立授权与引用发布流程，不由本次“上传”动作隐含批准。
- “仅生成预览”保留结果供后台查看，不写公开索引。之后点击“发布合格结果”创建新的、经授权的 publication run／attempt，关联已完成的生成结果，取得当前租约及 fencing token，重新检查当前权限、规则和人物／证据资格；不能恢复已结束、取消或过期的原运行权限。有效生成结果可复用，不无条件重新调用模型。
- 已发表 Signal 的页面／搜索／热点／资源更新仍经 Outbox；结果页分别显示“已生成”“已发布”“同步中／已同步”，不能把上传成功或任务完成当作网站已更新。

#### 批次进度、失败与审计

每项展示接收／安全检查／解析／提取／补证／发布／同步进度、对应 Signal 链接、可重试原因与用量。提供“仅重试失败项”“停止剩余处理”“查看已发布结果”，已成功发表的内容不因其他项目失败而回滚。

批次状态包括 uploading、queued、running、completed、partial_success、failed、cancelled；每项另记处理结果（processed、duplicate、deferred、failed 等）。**处理结束不等于全部发布**：页头分别统计输入项结果和去重后的 Signal 生成／关联已有／发布／暂缓数量，避免一文多事件造成计数误解。

一个文件失败不阻塞其他独立文件；多文档共同支撑的事件只有在足够证据到齐后才具备发布资格。预览及已生成但待发布内容可按新增证据重新核验，不能因提前失败永久丢弃跨文档合并机会。

本批预算与全局预算共同生效；每项有 token／解析／OCR 限制与费用记录。停止本批仅取消未完成步骤，并在发布事务前复查，不自动撤回已发布 Signal。批次详情、原件访问和重试接口都验证管理员身份和资源归属。

私有原件及解析产物设置保留期限和访问审计，取消后清理未完成上传；被正式版本引用的证据不能按普通临时文件直接清除。原件删除与 Signal 撤回是不同操作，保留可公开证据、最小审计与必要的版本关联，不能因清理批次静默破坏已有引用。

### 7.5 AI 配置、来源发现与自动更正

本节是产品侧必须提供的能力摘要，具体字段、执行与安全规则由 [专项设计](AUTONOMOUS_SIGNAL_PIPELINE.md) 第 4、5、8、9 节定义：

- **AI 配置**：协议适配器、HTTPS Base URL、模型列表与手填、连接测试、独立 Schema／能力测试；提取／核验／研判分别绑定 Profile，支持风格、长度、语言、参数与提示词版本。能力不足的模型不得分配给必要阶段；仅可切换预先配置且能力兼容的备用连接。密钥信封加密、根密钥与数据库分离、版本与掩码展示保留。
- **增量来源**：游标、ETag／Last-Modified、有界回看及失败重试；先持久化文章再推进游标，不因解析失败跳过输入。覆盖指标不能用空 HTTP 200 冒充有效采集。
- **新来源发现**：管理员提交的未知公开域名和自动发现的链接先进入受控临时抓取、来源身份／访问规则评估及证据核验；不强制逐条人工登记，也不因抓取成功自动授予官方／高可信身份。机器不能绕过既有来源准入或全局放宽 HTTPS／allowed_hosts 规则。
- **自动更正检测**：对已引用原文变更、来源撤稿、新支持／反证执行有界周期扫描；按重要度与来源频率配置复查周期，保存最近成功核查时间与下次计划，触发对受影响 Signal、人物关系及专题洞察的重新核验。仅链接失效不等于事实错误，不直接按 404 撤回。
- **更正处理**：核实影响后产生新版本或使当前公开资格失效；同步搜索、页面、榜单、资源及依赖洞察的更正提示。暂停自动新发表不能关闭独立授权的撤回／屏蔽能力；无事实变化不重复生成或更正。

## 8. 可解释评分与趋势

以下是待校准的 `ranking-v1`，实现为确定性纯函数与版本化快照；不得让模型直接写最终榜单。

### 8.1 热点 TOP 10

候选限定为窗口内发生、截至计算时已正式公开、证据及人物关系合格的不同事件。过滤 withdrawn、暂缓内容和只补录未发生新事件的旧消息。

建议初始公式，分项均为 `0..1`：

```text
HotScore = 100 × (0.35 × T + 0.25 × H + 0.30 × I + 0.10 × N)
T = 2 ^ (-事件距截止时间的小时数 / 48)
H = min(1, ln(1 + max(0, 独立证据归属组数 - 1)) / ln(5))
I = (importance - 1) / 4
N = 有依据的新颖度评分（0 / 0.5 / 1）
```

- `T` 用发生时间而非采集／更新日期；未来事件不当作已发生事件参与热榜。只有天级精度时按明确的日期约定计算并展示精度。
- `H` 首版明确叫“独立来源关注度”：一个官方来源可以构成合格信号，但不虚构它有高传播量；同一机构、同稿转载合并归属。只有经过核验且支持该事件的来源才计数。
- HZense 自产专题洞察及其转载不新增证据归属组；采集到回流内容必须追溯外部原始证据，避免“生成洞察 → 再采集 → 热度增加”的循环。
- 当前没有可靠的社交／站内热度指标，所以首版不引入虚构点赞量或浏览量。以后接入真实数据应另建评分版本，处理机器人、缺失值与平台差异。
- `I` 按影响范围、证据支持的技术／产业变化和约束变化做 1–5 量表，保存理由；5 不是“标题很轰动”。`N` 区分同事件更新、已有方向的实质增量、确有新机制／里程碑的变化。模型建议必须带理由，不能用其自报置信度决定事实真伪。
- 质量资格先过门禁再评分，不能靠新鲜度或热度补偿事实缺失。缺少必要评分依据时暂缓上榜，不静默设高值。
- 使用未四舍五入分数排序，展示一位小数；同分按事件时间倒序、稳定 ID 升序。公布窗口、分项、证据数与公式版本。
- 新一代产品发布与过去产品发布可分别成事件；仅报道刷新不得重新建 ID 获得新鲜度加成。

重要度初始量表：1 为常规维护／小范围信息，2 为单产品或团队的局部增量，3 为影响明确应用场景或生态的实质变化，4 为跨组织／关键技术路径或产业约束的显著变化，5 为有充分依据的结构性转折。每档必须写明“影响对象、变化幅度及依据”；估计影响与已证实效果分开，来源多不自动提高重要度。量表用标注样本校准，不将 AI 自评直接视为真实影响。

### 8.2 领域／专题趋势

首页趋势回答“本系统观测到的活动是否正在加速”，不把关注度自动解释为技术成熟度或长期价值。后两项由有证据的专题分析单独解释。

建议用最近 7 个完整本地日与此前 7 个完整本地日比较，使用同一时区、来源面板、数据水位与统计规则。只计截至该水位已正式公开、人物与证据合格、`occurred_at` 落在相应窗口的去重事件；候选、采集文档、日报／洞察篇数均不计入：

```text
C = 本期不同事件数
P = 前期不同事件数
变化率 = (C - P) / max(P, 3)
```

前期至少 3 个事件、本期与前期合计至少 6 个事件才判定涨跌。建议 `>= +25%` 且净增至少 2 为上升，`<= -25%` 且净减至少 2 为下降，其余平稳；`P < 3` 而本期显著增加标为“新近活跃／基数不足”，不展示无穷增长。

统计时同一领域内事件去重；跨领域事件允许各计一次。新接入来源、来源离线和人物补证导致的可见性变化都可能制造假增长：采用两期共同覆盖的来源面板，并显示全量事件数、比较面板和处理水位。

覆盖率按固定计划的“来源—日期”抓取、分页和解析完整性计算，不以 HTTP 200 或任务结束充当成功；不能临时减少计划分母来提高覆盖率。任一期低于建议 90%、关键来源缺失或面板变更未完成可比性核对，标记“覆盖不足／不可比”，不输出涨跌结论。另核对候选处理积压、人物补证／审核集中完成的影响；水位不齐也不得判涨跌。补录引起历史窗口重算时明确标为“历史数据修订”，不是新发生的产业加速。

每个快照保存窗口、来源面板、去重事件 ID／版本、规则版本与生成时间；人工样例快照和自动测算使用不同方法标识。实时热榜与完整日趋势截止点不同，界面分别注明。

### 8.3 组织活跃度

首版默认最近 30 天，对有证据的组织主体／参与事件去重后计算：

```text
Activity(org) = Σ 2 ^ (-事件距截止时间的天数 / 14)
```

以带时间衰减的不同事件数排序，体现“近期活动多的组织靠前”。同分先按窗口内不同事件总数，再按最近事件时间、稳定 ID；展示原始事件数、窗口、最近事件时间，不伪装成百分制质量评分。

只计正式合格 Signal；同稿转载、同事件多人物、同一组织多个别名都只计一次。零近期信号的旧组织仍可检索，但排在活跃组织后。更正／撤回重新计算所属组织，不能只增不减。

### 9.2 建议的逻辑模型（不是已存在的物理表清单）

| 模块              | 扩展／新增逻辑对象及契约                                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Signal            | 复用稳定 Signal ID；新增 publication 状态、不可变 `signal_versions`、`event_key`、当前有效版本                                                  |
| 时间              | `occurred_at`／精度／依据、`source_published_at`、`captured_at`、`published_at`、`updated_at`；不能相互替代                                     |
| 来源与证据        | 扩展 Source 配置；多来源证据、来源归属组、断言及片段定位、支持／冲突、可公开性与内容指纹                                                        |
| 人物／组织        | 复用 `entities` 的 person/company/institution ID；人物档案和组织档案作为类型化扩展，而非再建重复身份体系                                        |
| Signal—人物／组织 | 在 Signal 版本上固定事件角色、关联实体、证据与核验状态；通用 `signal_entities` 可作当前版本投影，不能成为第二套独立关系源                       |
| 任职关系          | 复用／扩展 `relations` 的方向、任职类型、有效区间和证据；区分当时与当前任职                                                                     |
| 专题洞察          | Topic 长期入口、`insight_editions`、输入 Signal 版本边、最新公开版指针、生成运行及修订理由                                                      |
| AI 执行           | 配置版本、计划、runs、steps、model_calls、费用预留／结算、私有输入与输出                                                                        |
| 批量导入          | import_batches、import_items、文档版本／对象引用、接收／处理状态、attempt、来源可见性及 item—evidence—Signal 版本多对多边；批次在模型调用前创建 |
| 公开投影          | publication_outbox、各消费者 checkpoint、search_documents、hot/trend/activity 快照                                                              |
| 审计              | 身份、时间、动作、版本、配置差异及脱敏失败原因；不存公开明文凭据                                                                                |

Signal 多人关联、组织角色及洞察证据必须能独立查询和约束，不能全部塞进无契约的 JSONB。具体表名、类型化外键、索引、约束及允许的触发器在迁移 PR 中冻结。

“公开版本至少一位合格 Person”是跨表规则，不能只写一个 `CHECK` 或前端 `min(1)` 就声称数据库保证。设计要求：发布事务锁定 Signal、版本及依赖的人物／证据资格；人物合并、类型变更、关系删除和证据撤销经同一协调入口，按固定锁定顺序重新检查所有受影响的当前公开依赖，必要时先使公开版本失效／撤回。以版本条件更新或可串行化重试处理并发，禁止 Worker 直接改公开指针。历史版本保持不可变，但不因此继续拥有公开榜单资格。若采用数据库延迟约束触发器作第二层防护，必须同步更新当前拒绝未知 Trigger 的 verifier 和最小权限契约，不能静默放开所有 Trigger。[PostgreSQL 约束说明](https://www.postgresql.org/docs/current/ddl-constraints.html) 对跨行 `CHECK` 的限制是这项实现选择的依据。

### 9.3 分开三种状态

- **处理状态**：queued、processing、retry_wait、needs_person_evidence、needs_public_evidence、deferred、rejected、completed、cancelled；批次／输入项另有自己的接收与汇总状态，不能与 Signal 状态混用。
- **内容状态**：unpublished、published、withdrawn、archived；已发布内容的新草稿失败不自动覆盖旧有效版。
- **投影状态**：pending、ready、degraded，以及每个消费者已处理的版本和滞后时间。

历史 legacy 档案单独标记，不把旧 accepted 直接解释成已通过新规则。事实更正创建新版本；错误涉及私有信息或失实核心断言时提供明确撤回流程和公开说明。

## 10. 应用与后台架构

继续使用当前 Next.js／TypeScript／PostgreSQL／Drizzle，不为一次重构顺便更换整套技术栈。采用服务端读取公开数据、客户端负责筛选／图表交互的边界，避免浏览器接触数据库凭据；与 [Next.js Server / Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) 的职责划分一致。

建议代码边界（待实施，不表示目录已存在）：

```text
apps/web/app/                 公共页面、admin、受保护入口
apps/web/components/          统一导航、Signal 行、人物卡、趋势卡、筛选器
apps/web/lib/server/          公共读服务、后台认证与任务提交
packages/database/            业务 Schema、迁移验证、事务与受限角色
packages/content/             历史内容兼容、Seed 导入校验、导出契约
packages/ingestion/           来源／批量导入适配、安全解析、事件去重与补证
packages/ai/                  模型适配、结构化输出、配置快照与用量
packages/intelligence/        热榜、趋势、活跃度、专题生成编排
packages/search/              统一发布版本的搜索投影与查询
apps/worker/                  持久化任务的分步执行入口
```

Worker 采用可部署的 Node.js 后台运行方式，第一版可基于 PostgreSQL 持久化任务和短时步骤；部署前实测任务时长、并发、续跑及费用，必要时使用独立托管 Worker。Vercel Web 请求只提交任务，不等待整批采集／深度分析。具体服务商和付费资源选择属于实施配置，不在本文虚构为已经开通。

### 10.1 发布与自动同步

同一事务写入不可变公开版本、当前状态和 Outbox；消费者幂等更新搜索、列表／实体投影、热点与趋势失效标记，再处理缓存。写入按实体版本单调前进，重复／乱序事件不能覆盖新版本。

建议服务目标：正常情况下发表至信号详情／搜索可见不超过 60 秒；热榜与资源活跃度不超过 5 分钟；完整日趋势每日重算，相关更正触发重算。这是待验收目标而非现有 SLA。延迟超限显示最后成功时间并告警，保留最后成功快照且标为过期，不能以 HTTP 200 宣称所有数据新鲜。

撤回优先于展示：查询搜索和聚合时核对当前公开版本，不从过期索引返回已撤回摘要；失效通知和有界缓存 TTL 配套。公开详情的撤回状态不能依赖长时静态缓存。外部已被阅读／缓存的内容无法保证追溯删除，需保留更正说明。

当前全量 Seed 搜索同步器必须在切换前变为按数据归属更新；旧 Seed 的缺项不能删除新的数据库 Signal／洞察。sitemap 的 `lastmod` 使用公开内容实际修订时间，事件日期保留为事件日期。

### 10.2 角色与权限

公众 Reader 只读通过发布资格校验、按所选策略正式发布的当前有效公开视图；后台配置、抓取 Worker、发布服务、投影消费者分别获得所需权限，数据库迁移身份不用于网站运行或模型工具。新增表、视图、函数、RLS／Trigger 与 verifier 必须整体评审；不通过全面放宽当前 Runtime ACL 来省略权限设计。

历史兼容使用独立的只读公开档案视图，仅包含切换前已公开且仍允许展示的内容；未公开候选、私有输入与后台日志不能进入该视图。待补证 legacy 可免于新版人物升级条件继续保留旧详情，但同样受统一撤回、隐私屏蔽与 tombstone 控制。档案查询必须显式选择，不能通过这个例外进入新版默认列表、热点、趋势或新洞察合格输入。

后台的任务触发、配置、合并人物、撤回接口都需要服务端授权、输入校验、Origin／CSRF 防护、速率限制与审计。模型不能直接运行管理员 API 或自行修改预算／发布政策。

### 11.2 数据切换顺序

1. 固化 Schema／发布契约，建立统一 repository；现有 Seed Reader 暂时保持服务。
2. 幂等导入 Sources、Entities、Relations、Signals；保留 ID、事实、事件时间、来源 URL 与旧状态来源，输出数量／ID／引用差异报告。
3. 对人物缺口逐条补证和消歧，补齐缺少的事件去重身份。满足新规则才升级到新公开版本；其余记录在 legacy 档案／暂缓队列，不假称 82 条都已通过。
4. 为旧 Topic／Insight 建立明确映射；先保留已有正文与引用，不让 AI 覆盖原文。
5. 在隔离预览环境核对旧链接、查询、聚合、搜索、人物与撤回行为。新人物规则通过前不能用临时 CEO 占位数据验收。
6. 单次权威切换：先提交内容就绪报告（已升级／留档／暂缓数量、近期信号及领域覆盖、可生成专题数），由操作者确认实际可见内容规模，不能把空站默认计为上线成功；随后停止 Seed 的正式 Signal 写入，切换数据库读和发布，防止旧全量同步覆盖新数据。停止自动任务时也不倒退成双写。
7. 新首页／专题与资源通过验收后，关闭旧 Daily 定时生成和自动 Draft PR 路径，移除日报／周报主导航；不在设计阶段执行停用或文件删除。
8. 保留历史渲染测试；用新版契约替代旧首页／日报产品断言。停用旧门禁需同时核对分支保护的 required checks，避免删工作流造成 PR 永久等待；通用 CI／数据库权限门禁不取消。

新旧数据不能都成为正式写入源。回滚优先暂停调度／发布并退回兼容新数据库的应用版本；切换后不能直接恢复旧 Seed 页面使新发表内容消失。保留导出与数据库备份方案，但本次设计不重新安排操作者已取消的恢复演练。

迁移验收保留 **ID、事件时间、来源、正文与历史 URL 可访问性的一致性**；由于新增人物规则及档案分离，不承诺新版默认列表、默认搜索和热榜与旧公开集合相等。差异必须逐项说明为“升级／留档／暂缓”，不能当作未解释的数据丢失，也不能以强行发布缺人物记录来凑齐旧数量。

## 12. 视觉与交互规范

- 延续 HZense 深蓝／蓝色、浅色与深色主题，不把结构重构误作品牌更换。
- 首页减少大面积口号和装饰图，把实时状态、趋势、热点放在首屏。
- 列表使用紧凑行；详情正文限制阅读宽度，中文行高与段落间距单独处理，避免长卡片和单字换行的大标题。
- 图表只服务于时间变化；图例、文字趋势和表格替代视图同时提供，不只依赖红绿颜色。
- 信号、人物、组织与专题的跳转可预期，当前筛选可见且可清空；状态标签不挤占标题。
- 移动端筛选抽屉、触控目标、键盘焦点和无障碍名称纳入验收；不能只验证桌面截图。
- 首屏不得用演示分数／模拟人物冒充当前数据。设计预览若使用占位内容，始终标注“示意”。

## 13. 实施顺序与验收

以下是交付依赖，而不是本次已完成项。不沿用旧 MVP 的完成百分比衡量本次新范围。

| 阶段              | 交付                                                                                                    | 退出条件                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| V2-0 设计基线     | 本文、主设计入口、专项技术契约及迁移边界                                                                | Signal 默认自动发表已统一；专题洞察默认策略和首次生产开关另行明确                    |
| V2-1 数据与关系   | 版本、证据、人物／任职契约、发布事务、历史导入 dry run                                                  | 缺人物／错人物／撤销关系被拦截，ID／时间／引用无损                                   |
| V2-2 后台采集闭环 | owner 登录、完整模型／来源配置、文档／表格／OCR／链接批量导入、生成并发布、自动任务、费用与自动更正检测 | 三入口默认自动发表，全格式能力验收；批次逐项可追溯、部分失败可重试、关闭网页仍可完成 |

| V2-5 专题洞察     | 固定专题、周度及手动任务、冻结证据、版本与比较                                                          | 两种触发共用流程，事实均可追溯，无实质变化不空写报告                                 |
| V2-6 迁移上线     | 分批切换、旧路由归档、Daily 停产、新验收与发布证据                                                      | 公开主路径闭环、历史链接可达、权限／版本／投影状态可核验                             |

必须覆盖的场景：

1. 自动发现一个新事件 → 提取并核实一位或多位人物 → 正式发表 → 信号、搜索、首页、资源均出现同一版本。
2. 同事件多个链接／转载、同名人物／组织、任职变动、多领域归属均不会错误倍增或合并。
3. 无人物、错误日期、冲突数字、私有来源、未来事件、来源超时、预算耗尽分别进入明确状态。
4. 时间／领域／趋势／关键词聚合可分享、刷新、翻页，统计基数一致；390px 移动端可读可操作。
5. 无近期信号、低基数、新增来源、来源离线和不足十条热点能诚实展示，不生成虚假繁荣。
6. 同一个专题定时与手动并发只产生预期版本；新增反证会更新结论或标记不确定，不覆盖历史正文。
7. 发布失败、重复 Outbox、消费者乱序、索引故障、缓存失效失败可恢复；撤回不从旧投影继续泄漏正文。
8. 新首页不再依赖日报／周报；旧内容和旧洞察 URL 仍可读，正文和来源引用没有被批量重定向丢弃。
9. 混合批量文档和链接触发生成并发布；一文多事件、多文同事件、重复输入与并发提交不重复发表；批次能区分输入项数量与去重事件数量。
10. 文件超限、伪造类型、解析失败、上传中断、链接失效分别呈现；仅重试失败项保留成功结果，停止批次不撤回已发布内容；必需证据未到齐的事件不会提前发表。
11. 私有材料缺公开佐证暂缓；恶意文件／网页不能修改模型系统规则或发布权限，公开页面、搜索、错误信息不泄漏私有附件、文件名或下载凭证。
12. 手动导入的“生成并发布”无需逐条二次确认，但仍受当前发布总开关、预算、证据与人物约束；预览模式不触发公开写入，同步未完成不得显示“全部上线”。
13. CSV／XLSX、扫描 PDF 和 PNG／JPEG OCR 实际产出带位置的有效证据；能力未配置／低质量识别不能用标准文本格式通过来代替完整首版验收。
14. 未注册公开链接经机器准入后可有界采集；来源增量失败不会跳过未持久化输入。原文更正／撤稿可自动触发复核，单纯链接失效不会误撤事实，依赖专题与搜索收到修订状态。
15. 模型列表／手填、分阶段 Profile、能力不足拦截、兼容故障切换、用量与费用记录均验证；暂停新发表时仍可通过独立授权路径屏蔽已确认泄漏或错误内容。
16. 旧公开档案仍可访问并受撤回控制，未公开候选不因迁移而公开；预览后发表创建新授权运行，旧租约／取消状态不能被复活。
