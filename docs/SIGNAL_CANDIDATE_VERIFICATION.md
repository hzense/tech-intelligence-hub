# Signal 受控核验记录与候选组装

## 1. 本批交付边界

承接 [0010 私有发表核心](SIGNAL_QUALIFIED_PUBLICATION.md)，新增 `0011` 的核验记录与组装回执，解决已封存人物／组织边不能原地从 `pending` 改成 `verified` 的断点。

```text
已封存候选 + 已核验公开原文 + 规范事件身份
  → 读取并绑定核验材料
  → 可信核验阶段提交通过／拒绝记录
  → 新版本候选组装、提交封存
  → 另一次受控私有发表事务
```

这是可信内部适配器，不是已接入模型的事实核验器，也不是管理员认证、生产 Publisher 或新版公开读取。三入口默认自动发表的产品策略不变；本批不接入前端、生产调度或生产开关。

支持／背景原文必须已有 `verified` 记录，未拒绝的反证仍阻断。已拒绝的历史反证按既有资格规则保留。本批**不更改共享 `public_source_evidence` 的状态**，也不会让候选组装顺带批准其他 Signal 共用的原文。原文核验执行器仍需后续接入。

## 2. 私有接口及信任边界

实现位于 [signal-candidate-verification-store.mjs](../packages/database/src/signal-candidate-verification-store.mjs)，规则位于 [candidate-verification.mjs](../packages/database/src/candidate-verification.mjs)。均不从包根导出，不新增路由、命令或生产授权。

| 接口                                       | 输入与结果                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `readPrivateCandidateVerificationMaterial` | 仅 Signal ID 和已封存来源版本；返回完整核验材料及指纹                                                                 |
| `recordPrivateCandidateVerification`       | 材料指纹、来源版本／哈希、核验者 ID、固定规则版本、六项检查、通过／拒绝结论、1–86400 秒有效期；重新锁读匹配后保存记录 |
| `assemblePrivateVerifiedSignalCandidate`   | 仅幂等请求键、核验记录 ID、Signal、来源／目标版本；不接收正文、`verified` 标记、回调或 SQL                            |

核验者 UUID、材料哈希、核验记录 ID **不是认证**。记录入口只能由可信核验阶段调用，不得直接连接用户表单或模型原始输出。六项检查记录断言覆盖、人物消歧、人物确为事件参与者、组织支持、公开来源许可、反证处理；`approved` 要求六项均为真。它们是可信阶段的结构化核验结论，不意味着本模块自己阅读网页、证明事实或独立完成隐私审查。未来真实执行器负责形成这些结论及其审计链。

`hzense_runtime`／`hzense_signal_writer` 不获得新表或守卫函数权限。具有 owner DDL／任意 SQL 能力的管理者仍在外部信任边界，不能把私有接口包装成对 owner 攻击的隔离系统。

## 3. 材料绑定与新版本

不能只使用快照 `content_hash`：该哈希不包含关系边。核验指纹覆盖：

- 完整快照、四类边及其原始 `pending`／`verified` 状态。
- 规范事件身份完整字段、旧身份依据版本的全部证据边；不允许遗漏旧版本反证。
- 原文 URL、定位、片段、内容哈希及事件／采集时间。
- 当前 Source、Evidence、Entity、类型化档案及 Topic 投影。
- 人物／组织名称、别名及元数据，以及来源名称、类型、URL 与信任分值。元数据对象规范键顺序，数组保留语义顺序；另绑定数据库 `metadata::text` 原始 JSONB 文本，避免 JavaScript 数值解码丢失高精度后指纹碰撞。核验材料同时返回该精确文本。

材料集合顺序不影响指纹，正文不做改写；未知字段、重复或无关记录、异常对象及超限依赖拒绝。数据库先检查日期有限、UTC 年份 1–9999 和毫秒精度，避免驱动截断微秒后误认内容一致。

新组装必须重新锁读并匹配完整指纹，拒绝源内容哈希、Signal／版本或当前依赖错配。已有规范身份是前置条件，不在本批创建或改写身份。缺人物、支持证据不足、人物／组织 `rejected` 或当前来源失效时不能组装。

只有新版本的人物／组织边可以依据通过记录写为 `verified`；保留所有证据／Topic／人物／组织边，不过滤掉失败边再发表。目标版本必须大于该 Signal 的全部已存在版本。正文、研判、事件时间、采集时间和来源语义保持不变，只有版本号和规范正文哈希变化。源版本完全不动。

## 4. 事务、有效期和重试

材料读取与记录入口保持短事务；网络与模型调用在事务外完成，提交结果时再比较指纹。组装锁序为请求键 → 核验记录消费锁 → 核验记录 → Signal → 来源版本／身份 → Source → Evidence → Entity／档案 → Topic。依赖锁沿用现有发表核心的顺序。

`verified_at` 取本次 INSERT 的毫秒级 `statement_timestamp()`；它是记录入库时间，不是事件时间，也不证明核验工作发生的时间。过期检查使用等待后的 `clock_timestamp()`，两者差异见 [PostgreSQL 时钟说明](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)。有效期最长 24 小时。

核验记录必须先提交，组装不能使用同事务中临时制造的记录。新版本及回执共同提交；写前、[延迟约束触发器](https://www.postgresql.org/docs/18/sql-createtrigger.html)以及约束执行后的最终检查均要求记录有效。失败回滚新版本和全部边，不留下部分成功。最后检查后立即提交，不承诺存储提交耗时也在截止时间前。

- 同一核验 ID 只能重放完全相同的结论、材料、核验者和有效时长；不能更新记录续期。
- 每个核验记录最多消费一次。不同请求键竞争时最多创建一个新版本。
- 相同组装请求只返回 `private_historical_assembly` 回执，不重新组装、恢复发表或授权公开；换目标／记录／来源等语义字段拒绝。
- COMMIT 结果不明时用相同请求键重试，不能自动换键。

**有效期只约束新的候选组装。** 它不是长期公开许可证，现有 `0010` 也不将该期限自动解释为后续发表资格。已组装内容的发表仍另行检查当前依赖、任务、授权、取消和租约；完整公开资格、撤回与依赖失效协调留在下一阶段。核验与候选组装不受新增发表总开关限制，因此可以服务预览；这不表示已完成后台的三策略任务流程。

## 5. 物理结构与后续

`0011_signal_candidate_verification.sql` 追加两张私有表：`signal_candidate_verifications` 和 `signal_candidate_assembly_receipts`。复合外键精确绑定来源版本、核验记录和目标版本；记录／回执禁止 UPDATE、DELETE、TRUNCATE，事务戳防伪造封存，目标要求在本事务创建并匹配哈希。

仓库目标变为 **12 个迁移、33 张表（32 ORM + 1 历史账本）、8 个守卫函数、29 个 ALWAYS 触发器**。Drizzle、manifest、独立 catalog、Schema／Runtime／Topic 预检与角色拒绝测试同步更新；不改历史 `0000`–`0010`、旧角色授权或生产配置。

接下来依次完成真实认证及受限 Publisher、当前公开资格／独立撤回／消费者，再接 AI 任务和批量导入后台，最后实现新版页面及生产迁移。本批不把这些后续事项计作完成。
