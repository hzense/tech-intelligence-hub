# 四张未使用表退役

2026-10-09：本批交付退役代码、文档和测试，验证范围见下文；合并及应用部署不执行生产迁移。`0031_retire_unused_tables.sql` 的仓库目标为 32 项迁移（0000–0031）、58 张持久表，其中 57 张应用表、1 张 `hzense_schema_migrations` 账本。最近已归档的生产状态是 2026-10-08 统一 Signal 切换验收时的 31 项迁移、62 张表；本说明不构成新的生产检查或退役完成证明。

## 范围与依据

| 退役表                   | 当前用途核查与替代路径                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `content_registry`       | 未找到当前业务 SQL 或 Drizzle 读写；Markdown 正文与元数据由 `apps/web/lib/content-runtime.ts` 从文件加载，搜索使用 `search_documents` 投影。 |
| `entity_topics`          | 未找到当前业务读写；资源页由 `apps/web/lib/resource-presentation.ts` 汇总实体关联 Signal 的领域，实体登记不写独立 Entity—Topic 关系。        |
| `radar_snapshots`        | 当前首页通过 `buildSignalRadar` 从公开 Signal 与 Taxonomy 构建雷达；统一模式的旧 Seed 快照读取返回空数组。                                   |
| `radar_snapshot_signals` | 旧 Radar 快照的证据边；未找到现行业务读写，与旧快照表成组退役。                                                                              |

审计区分了业务访问、历史迁移与维护校验。旧 `0000`／`0001` 的建表及回填语句、Drizzle 声明、Verifier 查询和历史 ACL 记录不构成现行业务使用，但退役实现必须处理这些当前维护依赖。已知四表之间只有 Radar 证据边指向快照表；仓库未发现其他现行业务视图、函数或用户触发器依赖它们。执行时 PostgreSQL 已登记的未知依赖由 `RESTRICT` 阻止；字符串函数体或仓库外动态 SQL 仍需另行盘点，不能用静态搜索代替执行时核验。

本批不删除 `sources`、`relations`、任职／证据／规范事件身份或其他 3.0 兼容表，也不删除 `editorial_signal_revisions`、`legacy_signal_archive` 等来源和审计记录。统一 Signal 的主表、版本正文、公开视图、发布状态及读写开关不变。既有 Radar Enum、Seed／Markdown 文件、旧迁移及校验和保留。

## 迁移停止条件与数据保护

迁移执行器把本文件的全部 DDL 与 0031 账本记录放在同一事务中。迁移首先以固定表名取得四表的 `ACCESS EXCLUSIVE` 锁，再检查结构与是否存在记录，防止空表检查后并发写入。

- 四个目标必须存在，且为当前执行角色所有的普通持久表；缺表、分区／继承关系、外部表、unlogged 表或所有权漂移均不能被静默接受。
- 任一目标开启 RLS／FORCE RLS、存在 Policy、用户触发器或重写规则时停止，避免隐藏记录或顺带删除未审核逻辑。
- 任一目标存在至少一行即抛出 `unused-table-retirement-nonempty`，不清空数据、不覆盖旧记录，也不自动归档后继续。需保留现场并另行审查数据用途。
- 先删除 `radar_snapshot_signals`，再删除 `radar_snapshots`、`entity_topics`、`content_registry`，每次均使用 `DROP TABLE ... RESTRICT`。不使用 `CASCADE`；其他表的外键、视图等未审核依赖会阻止退役。
- 任一步失败，0031 的全部删除及账本登记一起回滚；执行器此前已提交的历史迁移不受影响。成功后的重跑依据账本跳过 0031，不重放删除。

本批的成功条件是四表确实为空且满足结构与依赖边界，不是“空表查询大概没有返回数据”。若提交结果未知，应先独立只读核验账本和对象状态，不自动重试。

## Schema 与维护兼容

当前 Drizzle 与独立 Verifier 移除四表的列、主外键、约束、默认值和索引契约；旧 Radar 的 SQL 完整性查询不再对最新 Schema 执行。完整校验目标为严格的 58 张表，旧表在 0031 后重新出现也会被判为结构漂移。

迁移前预检先验证 manifest 和迁移账本。只有确认 `0031_retire_unused_tables.sql` 仍待执行时，才在最新版集合之外接受这四个明确的历史表；未知表仍被拒绝。这一过渡规则仅用于迁移前预检，不放宽 Runtime Reader、Topic Sync 或 ACL 合约。未升级数据库运行最新版严格预检时会报告结构差异或待迁移，不应绕过错误继续业务同步。

历史 `0000`／`0001`、foundation 基线识别、旧阶段的受保护批准清单及生产证据保持原样。旧 Radar 回填测试继续验证其对应历史阶段；最新 Schema、权限拒绝与漂移测试改用仍存在的表，并为退役成功、非空拒绝、结构／依赖漂移和事务回滚提供独立覆盖。

## 本地验证结果

- 数据库默认测试：105 个文件通过，3,048 项通过，831 项环境相关测试跳过。
- 隔离 PostgreSQL 18.4：退役、统一回填和切换发布链路合计 42 项通过、2 项预检跳过；其中退役 26 项通过，验证四表非空／缺失、视图与外键依赖、RLS／Policy／触发器／规则／继承、排他锁、失败账本不变及成功重跑幂等。
- 本地 PostgreSQL 没有 pgvector，仅使用已有的限本地 `HZENSE_UNIFIED_NO_VECTOR=1` 模式。CI 明确拒绝该模式；完整 pgvector、32 项迁移后的严格 Schema／ACL 及真实升级前后预检必须由 CI 继续验证，不能由上述 42 项推断已通过。
- 全项目默认测试通过（包含未受影响包的 Turbo 缓存命中），Web 本轮 878 项通过、13 项环境测试跳过；五个包的类型检查、数据库 ESLint、格式／差异检查通过。新增退役集成套件已接入 `test:migrations`。
- 独立静态依赖审计及代码复审未发现阻断问题；没有连接生产库、改变角色授权、调用 AI 或执行正式发布／撤回。

## 生产执行边界与恢复

本轮仅交付代码、文档和测试，不写生产。后续生产退役须先完成代码评审及 CI，核对当时数据与依赖，建立新的可恢复备份、恢复证据、ACL 基线和维护冻结，并取得绑定本次提交／运行／attempt／有效期的批准。历史统一切换备份和审批不能复用。

**迁移前尚待补齐的兼容项：** `verify-restored` 调用同一严格 Runtime Reader 预检，最新版要求 58 表，不能直接验证仍为 0030／62 表的恢复副本。生产执行前必须另行完成受审核的备份 Schema 版本匹配及恢复核验路径，不能跳过该检查或仅凭本 PR 宣称已满足恢复门禁。此限制不影响本次应用代码部署：Web 在线读取和健康接口不调用完整 Schema 预检，构建、启动也不会自动迁移数据库。

使用既有 `Production maintenance` 的普通 `migrate`，沿用 `recoveryPolicy=verified` 的恢复与审批门禁；迁移后再运行独立只读 `verify`，核对 32 项迁移、58 张表、四表缺失及保留对象契约。之后分别核对数据库健康、公开 Signal、雷达、资源和搜索。普通 ACL 基线采集读取 PostgreSQL 目录，不依赖最新版 Runtime 表清单，无需放宽权限来采集退役前的 62 表状态。

不使用冻结在 31 项迁移／62 张表的 `unified-signal-apply` 或 `unified-signal-verify`：它们属于已完成的统一切换批次，不能扩展为此次退役授权。`migrate-and-verify` 的既有特殊批次批准也不自动适用于 0031。

提交前失败由事务回滚；提交后需要恢复时，使用本次已审核备份与恢复流程，核对恢复后的数据、Schema、账本、ACL 及应用兼容性。不能仅重建四个空表、删除 0031 账本或切回旧代码来宣称恢复，也不提供伪造历史状态的自动 down migration。具体恢复操作仍需新的受保护维护批准。
